# v0.5-a2a-over-nexus: the Supervisor asks Finance itself

**Goal.** The Support Supervisor reaches the Finance Refund agent on its own. In
`run()` it discovers Finance's A2A Agent Card (the sync Nexus operation
`get_agent_card`). When a refund is eligible it calls `ask_finance_agent`, an
**async in-workflow Strands `@tool` that awaits the `send_message` Nexus
operation**. The server routes that call through the endpoint `finance-agent` into
namespace `agent-services`, where Finance's own Worker runs the A2A task
`a2a-task-<support id>`. The result comes back as the tool's answer, and the
Supervisor quotes Finance's refund ID to the customer. `SUPPORT_A2A_MODE=handoff`
keeps the runbook's explicit-handoff fallback one env var away. Both modes are
built and tested.

**Why now.** This is the central idea of the demo, and it carries the riskiest
library question, Q19a: can an in-workflow agent tool await a Nexus operation?
Answering it on the laptop means v0.7 onward builds on a known shape. v0.4 proved
the endpoint, the namespaces and the contract with no LLM, so anything that broke
here could only be the plugin or the prompt.

> **Status at hand-off: offline complete and verified; the live Bedrock runs are
> pending (justified deviation, same cause as v0.2–v0.4).** On 2026-10-29,
> `aws sts get-caller-identity` returns `InvalidClientTokenId` and `make bedrock-ping`
> fails with `TokenRetrievalError: … Token has expired and refresh failed`.
> `aws sso login` needs a browser, so no live LLM run was possible. Q19a, the
> handoff mode, the prompt-drift guard, crash safety and the cross-namespace hop
> don't depend on the model, and all of them are proven against a real dev server
> with real Worker processes. Two things are still live-only and carried as ledger
> item 49: "Case A end to end with live Bedrock" and the plan's "5 live runs, Finance
> called every time". Both are one command each (see "Live runs to do").
> **Gate G1 is not triggered:** Q19a passes, so `tool` stays the default.

## Which samples and docs it follows

- **samples-python**
  - `strands_plugin/tools/workflow.py`: the agent is built in the Workflow, plain
    Strands `@tool` functions run in Workflow context next to `activity_as_tool`
    tools, and the agent is run with `invoke_async`. `ask_finance_agent` is that
    sample's "pure Strands tool" pattern, made `async` so it can await (the sample's
    sync `letter_counter` does **not** work inside a Workflow with strands-agents
    1.62; see ledger 53).
  - `hello_nexus/caller/workflows.py` and `nexus_messaging/callerpattern/caller/workflows.py`:
    `workflow.create_nexus_client(service=…, endpoint=…)` created in the Workflow,
    then `execute_operation(...)`, with the contract imported through
    `imports_passed_through()`. The caller knows nothing about how Finance
    implements the operations.
  - `hello_nexus/handler/service_handler.py`: the stub Finance handler mirrors the
    real one (`sync_operation` card, `workflow_run_operation` task).
  - `strands_plugin/human_in_the_loop/workflow.py` and `activity_interrupt`: the
    agent stops, `run()` does Workflow work, then calls `invoke_async` again with new
    input. That is the shape of handoff mode.
  - `strands_plugin/structured_output`: deliberately **not** followed for handoff.
    It forces `tool_choice`, which Opus 5.5 refuses (ADR-0001 §6), so handoff uses
    an unforced capture tool.
  - `bedrock_agentcore/strands_agent/workflows.py`: prompt constants, and Activities
    passed through the sandbox.
  - `tests/strands_plugin/tools_test.py` (plugin appended through `client.config()`,
    `max_cached_workflows=0`) and `tests/hello_nexus/hello_nexus_test.py` (endpoint
    created per test and deleted afterwards).
- **temporal-developer skill**
  - `python.md`: `@workflow.init` when Workflow state depends on the input (here the
    A2A mode picks the Supervisor's tools and prompt); Workflows and Activities in
    separate files.
  - `gotchas.md`: pass-through imports; no blocking calls in Workflow code; test
    failure paths and replay.
  - `determinism.md`: the mode is a Workflow **input**, not an env var read in
    Workflow code, so it is in history and replays.
  - `testing.md`: `start_local` shared for cross-namespace tests, time-skipping where
    the Workflow layer is enough, a unique task queue and ID per test, replay from
    JSON, mocks by name.
  - `error-handling.md`: Nexus errors follow the same retryability rules as
    Activities. The caller handles `NexusOperationError` explicitly instead of
    letting it fail the Workflow.
  - `ai-patterns.md`: version prompts in code; Temporal owns retries; the pydantic
    converter comes from the plugin.
- **Temporal docs** (searched with the docs MCP tool)
  - "Strands Agents integration": run tools that do I/O as Activities, and keep
    deterministic tools in the Workflow. Always use `invoke_async`, never `agent()`.
  - "OpenAI Agents SDK integration › Nexus operation tools": `nexus_operation_as_tool`
    exists only there, which confirms Q19's second half is a real gap for Strands.
  - Nexus "Error Handling" and the Failures reference: an operation fails the caller
    with `NexusOperationError` (cause = the handler's failure), and only the caller's
    schedule-to-close timeout times an operation out.
  - Python API reference for `NexusClient.execute_operation` (`summary`,
    `schedule_to_close_timeout`, `cancellation_type`) and `NexusOperationError`.
  - Installed source, where the docs were thin: `strands/tools/decorator.py`
    (coroutine tools are awaited; sync tools go to `asyncio.to_thread`; exceptions
    become error results), `strands/tools/executors/*` (no tool timeout),
    `temporalio/workflow/_nexus.py` (the `execute_operation` signature, including the
    experimental `event_groups`, which is not used here).

## Run it

```bash
make setup                                  # once
# Offline (no AWS):
make dev-server-up
make payments-mock &  make worker-finance-scripted &  make worker-support-scripted &
make nexus-endpoint
make case-a                                 # tool mode: reply quotes R-1000x
make timeline WF=support-1042               # both sides of the hop, A2A conversation side by side
make task-state WF=support-1042             # Finance's view: a2a-task-support-1042 (agent-services)
make a2a WF=support-1042                    # Supervisor's view: card, exchange, guard re-prompts
SUPPORT_A2A_MODE=handoff make case-a WF=support-1042-handoff   # the fallback: same answer
make case-b                                 # $450: Finance rejects (approval arrives in v0.6)
make e2e                                    # Cases A and B against this running stack
# Live (needs aws sso login):
make dev && make case-a                     # honcho: dev server, payments, Finance + Support on Opus 5.5, endpoint
```

**What to look at.**
- Web UI, namespace `agents`, Workflow `support-1042`. The first event is the Nexus
  operation "A2A → Finance Refund Agent: get_agent_card (discovery)". Then come
  `invoke_model [Support Supervisor]` turns with the sub-agents' turns nested between
  them. Then, **between two Supervisor turns**, "A2A → Finance Refund Agent:
  send_message (refund order 1042 $40.00) via ask_finance_agent tool". Its link jumps to
  `a2a-task-support-1042` in **agent-services**, where the Finance Refund agent's own
  turns, `fraud_score`, `refund_history` and `issue_refund [Payments: …]` ran on
  Finance's Worker.
- `make timeline` prints the same thing in a terminal, followed by "Support → Finance:
  …" and "Finance → Support: [completed] Refund R-… issued …" side by side.
- With the handoff mode, the `send_message` sits *after* a Supervisor turn that ends
  with "Your refund request is with the Finance team", and before the reply turn.

## Talk track

"Support can't move money, so it asks Finance: a different team's agent, through a
published contract and a named endpoint. Look at the history. The first thing the
Supervisor does is read Finance's Agent Card over Nexus. Then its own sub-agents work
out the facts. Then, in the middle of the Supervisor's thinking, there's a Nexus
operation, `send_message`, and the link takes you into another namespace, where
Finance's own agent decides and issues the refund. It isn't a child workflow, and only
the contract is shared. If I kill the Support worker after Finance answered, the new
worker replays the answer from history; Finance is never asked twice."

## Deviations

- **Live Bedrock not run** (AWS SSO session expired, as at v0.2–v0.4). Everything
  else is verified offline against a real dev server. The live steps are scripted and
  carried as ledger item 49.
- **The caller's 25 h Nexus budget is a constant in Workflow code** (`SEND_MESSAGE_TIMEOUT`),
  not read from `SUPPORT_NEXUS_SEND_TIMEOUT`: Workflow code can't read the
  environment. v0.6 (ADR-0009) decides whether to pass it as Workflow input.
- **`make dev` also applies the endpoint**, through a Procfile entry that stays up
  after applying, because honcho stops everything when one process exits.
- **Support's Workflow-layer tests use a stub Finance**, not the real Finance Worker,
  so the team boundary holds in tests too. The real cross-namespace hop is in
  `tests/test_supervisor_a2a.py` and the verify script.
