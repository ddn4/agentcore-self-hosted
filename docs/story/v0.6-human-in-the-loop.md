# v0.6-human-in-the-loop: Finance waits for a human, Support waits for Finance

**Goal.** The Finance Refund agent may now say "I need a human". Over the $100
auto-approval limit, or at HIGH fraud risk, its A2A task goes to **`input-required`**
and waits, durably, for a Finance approver's **`approve`** or **`reject`** signal, for at
most `FINANCE_APPROVAL_TIMEOUT` (default 24 h). No decision in time ends the task
**`failed`**. The `get_task` query shows the task at every step. On the other side of the
Nexus hop, the Support Supervisor simply keeps waiting inside its `ask_finance_agent` tool,
on a budget of **25 h** (`SUPPORT_NEXUS_SEND_TIMEOUT`, ADR-0009). It apologises on
`rejected`, apologises and escalates on `failed`, and still catches `NexusOperationError`.
The Support Worker can be switched off for the whole wait: the approval completes Finance,
and the next Support Worker finishes the conversation.

**Why now.** This is the behaviour that justifies serverless Workers (v0.7 onward): the
caller can wait for hours at no cost. It is proven here on the laptop, with real processes,
before the Worker becomes an AgentCore session that drains while it waits.

> **Status at hand-off: offline complete and verified, including a 31-minute real wait;
> the live Bedrock run is pending (justified deviation, same cause as v0.2–v0.5).** On
> 2026-10-29 `aws sts get-caller-identity` still returns `InvalidClientTokenId`

## What it adds

| Area | What |
|---|---|
| Finance task Workflow | `FinanceAgentTaskWorkflow`: after the agent's assessment, `policy.decide()` (code) picks auto-approve or `input-required`. The task message names the amount, the reason ("over the $100 auto-approval limit" or "risk HIGH"), the wait limit and the signal to send, plus the agent's assessment for the approver. `workflow.wait_condition(..., timeout=, timeout_summary="Finance approval wait")`: approve → `working` → `issue_refund` (task ID as idempotency key) → `completed` with `approved_by=<approver>`; reject → `rejected`; `TimeoutError` → `failed` ("No Finance approver decided within 24h"). `workflow.set_current_details()` shows the A2A state on the Web UI's Workflow page |
| Signals and query | `approve` / `reject` take `ApproverDecision(approver, comment="")` (`finance_agent/policy.py`). Sync handlers that only set state; a decision outside `input-required`, a second decision or a blank approver is logged and ignored. `get_task` (v0.4) is unchanged |
| Approval timeout | `finance_agent.config.approval_timeout()` reads `FINANCE_APPROVAL_TIMEOUT` (`24h`, `5s`, `1h30m` …; `durations.py`), refusing anything above the published limit. | Contract | `finance_a2a_api.APPROVAL_WAIT_LIMIT = 24 h`; the Agent Card (now **v1.1.0**) says "waits in state input-required for up to 24 h, then ends failed". Golden file refreshed |

## Which samples and docs it follows

- **samples-python**
  - `strands_plugin/human_in_the_loop/workflow.py` and `run_workflow.py`: the Workflow (not
    the model) waits with `workflow.wait_condition`, a sync `@workflow.signal` sets the
    decision, a query exposes what is pending, and the starter polls the query before it
    signals. ADR-0002 explains why the gate is a code `if` rather than that sample's
    `BeforeToolCallEvent.interrupt()` hook.
  - `message_passing/introduction/workflows.py`: a dataclass signal input (`ApproveInput` →
    `ApproverDecision`), sync signal handlers that only mutate state, a query that never
    mutates.
  - `hello_nexus/handler/service_handler.py`: the workflow-run operation now also passes a
    memo through `ctx.start_workflow(...)`; `hello_nexus/caller/workflows.py` unchanged
    (`execute_operation` with `schedule_to_close_timeout`).
  - `strands_plugin/tools/workflow.py`: agents built in the Workflow, `invoke_async`, async
    in-workflow tools (the A2A tool simply awaits for longer now).
  - `tests/strands_plugin/human_in_the_loop_test.py` (plugin appended via `client.config()`,
    `max_cached_workflows=0`, signal from the test). That test signals right after start; our
    Workflow ignores a decision that arrives before `input-required`, so our tests first poll
    `get_task`, as the sample's `run_workflow.py` polls `pending_approval`.
    `tests/hello_nexus/hello_nexus_test.py`: endpoint created per module and deleted after.
- **temporal-developer skill**
  - `patterns.md`: "Wait Condition with Timeout" (`asyncio.TimeoutError`, i.e. the builtin
    `TimeoutError` on 3.12); signal and query handlers; "signal handlers should generally be
    non-async"; queries must not mutate.
  - `testing.md`: time-skipping for durable timers (Finance's 24 h), `start_local` for the
    two-namespace paths, "Testing Signals and Queries", unique IDs and queues, failure
    paths, replay.
  - `determinism.md` / `gotchas.md`: configuration reaches Workflow code as an input or memo,
    never as an env read; no I/O in Workflow code; pass-through imports.
  - `python.md`: `@workflow.init` so the task and its decision exist before the first signal.
- **Temporal docs** (docs MCP tool)
  - Nexus "Operations › Timeouts / Cancelation / Termination": schedule-to-close ends the
    operation for the caller (`NexusOperationTimedOut`); only cancellation reaches the
    handler Workflow. This is the core of ADR-0009.
  - Python "Workflow parameters" and "Data conversion": prefer a single dataclass input; with
    multiple parameters the SDK falls back to untyped decoding when counts differ (and the
    community threads describing the `dict` fallback). Ledger 58.
  - Python message passing: prefer dataclasses for signal inputs.
- **Installed source**, where the docs were thin: `temporalio/workflow/_context.py`
  (`wait_condition(timeout=, timeout_summary=)`, `memo_value(type_hint=)`,
  `set_current_details`), `temporalio/nexus/_operation_context.py`
  (`WorkflowRunOperationContext.start_workflow(memo=...)`),
  `temporalio/worker/_workflow_instance.py::_convert_payloads`,
  `strands/tools/executors/_executor.py` (no tool timeout; the `GeneratorExit` log on
  eviction, below).

## Run it

```bash
make setup                                   # once
# Offline (no AWS):
make dev-server-up
make payments-mock &  make worker-finance-scripted &  make worker-support-scripted &
make nexus-endpoint
make case-b                                  # starts support-2077 and returns
make task-state WF=support-2077              # Finance: input-required, the assessment, what to send
make pending WF=support-2077                 # Support: RUNNING, one pending Nexus op (send_message, 90000s)
# stop the Support worker (Ctrl-C); wait as long as you like
make approve WF=support-2077 APPROVER=dana.finance COMMENT="photos checked"
make task-state WF=support-2077              # completed, refund_confirmation approved_by=dana.finance
make worker-support-scripted &               # Support picks the conversation up
make result WF=support-2077                  # the reply quotes Finance's refund ID
make approval-report WF=support-2077         # both histories: how long it waited, who approved
# Reject instead: make case-b WF=support-2077-r; make reject WF=support-2077-r APPROVER=dana.finance
# Timeout path: FINANCE_APPROVAL_TIMEOUT=5s make worker-finance-scripted; CASE_B_WAIT=1 make case-b WF=b-t
# Live (needs aws sso login): make dev, then the same case-b / approve / result
```

**What to look at.**
- Web UI, namespace `agent-services`, Workflow `a2a-task-support-2077`: "Current details"
  says **input-required**; the timer "Finance approval wait" (24 h) is pending; after
  `make approve` the history shows `WorkflowExecutionSignaled approve
  {"approver":"dana.finance",…}`, the timer canceled, then `issue_refund`.
- Namespace `agents`, Workflow `support-2077`: the `send_message` operation stays
  **Started** for as long as the human takes, with no Workflow Tasks in between; with the
  Support Worker off, `NexusOperationCompleted` arrives and waits in history until a Worker
  comes back.

## Talk track

"Over $100, Finance's agent says 'I need a human', and the task goes to input-required.
Look: the A2A task in Finance's namespace says input-required, and Support has exactly one
thing pending, the Nexus call to Finance. I switch Support off completely. Nothing is lost:
the conversation is in history, and the server holds the call open. Now the approver
signals. Finance issues the refund, the answer lands in Support's history, and when a
Support worker comes back, the conversation picks up again and quotes the refund. The model
recommended; the approval rule is code. If nobody decides within 24 hours, Finance says
'failed', and Support apologises and escalates. Support budgets 25 hours on purpose, so
that it always hears Finance's answer instead of a timeout."

## Deviations

- **Live Bedrock not run** (AWS SSO session expired, as at v0.2–v0.5). Step 10 of the verify
  script is the live Case B with `make approve`; `make e2e` against `make dev` covers Case B
  approve and reject with real models.
- **The approval timeout reaches Finance's Workflow in the memo, not as an input** (ledger
  58, ADR-0009). The runbook sketch hard-codes 24 h; the plan asks for an env var, and
  Workflow code can't read one.
- **Supervisor-side approval tests run in seconds of real time**, because the time-skipping
  server does not skip through an open Nexus operation (ledger 56). Virtual 24 h is tested on
  Finance's Workflow alone; real minutes by verify step 9.
- **`make case-b` no longer waits for the reply** by default (a human is now in the loop);
  `CASE_B_WAIT=1` restores the old behaviour, `make result` waits afterwards.
- **Agent Card bumped to v1.1.0** (new behaviour and the published wait limit in its
  description). The schema is unchanged.
- **Older verify scripts no longer pass on this code:** `v0.4`/`v0.5` expect Case B (and the
  $450 smoke) to end `rejected` immediately. As with v0.2, run them from their tag's checkout.
- **Noise, not a defect:** when a Support Worker shuts down while the Supervisor is parked in
  `ask_finance_agent`, Strands logs `tool_name=<ask_finance_agent> | failed to process tool`
  with `GeneratorExit` as the evicted Workflow is garbage-collected. Nothing is written to
  history; the next Worker replays and continues (step 5, the stopped-Worker test).
