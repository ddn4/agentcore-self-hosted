agentcore-self-hosted · v0.13-scale-to-zero

Support asks Finance for a refund, across two namespaces

A Support Supervisor agent in namespace agents asks a Finance Refund agent in agent-services for money back, over an A2A-shaped contract carried by Temporal Nexus. Both are Strands agents on Claude Opus 5.5 (Bedrock), made durable by the Temporal Strands plugin, on a self-hosted Temporal 1.32 server.

System at a glanceLocal viewAWS view

Two teams, two namespaces, one server. The only code the teams share is the contract package finance_a2a_api. Workers never talk to each other: each opens an outbound gRPC connection to the frontend, and the server routes the Nexus call from agents into agent-services.

Inside the Support agentSame in both

support_agent/agents.py builds three TemporalAgents and the Supervisor's tools. The agents themselves are objects in Workflow memory. Everything that touches the outside world (a model turn, an order lookup, the policy file, Finance) leaves the Workflow as an Activity or a Nexus operation.

Where the agents actually execute

The A2A hop, Case B ($450, needs a human)Same in both

Support cannot move money, so its ask_finance_agent tool awaits the send_message Nexus operation. Finance treats the request as an A2A task. Above $100, or at HIGH fraud risk, the task waits for a person.

A2A task statesSame in both

The Finance handler Workflow is the A2A task. The get_task query returns its current state; the terminal task is the Nexus operation's result.

Serverless lifecycle: one conversation, two sessionsLocal viewAWS view

The Support Worker is built to die. It starts when it is invoked, drains after a short idle debounce, and a new invocation picks the conversation up when Finance answers. PINNED versioning keeps both lifetimes on the same Build ID. Locally (scenario 3) each lifetime is the AgentCore app on :8080; you invoke it with make invoke-local, and it drains 20 s after its last Activity.On AWS (v0.13) each lifetime is a separate AgentCore session in VPC mode, invoked by the WCI on EKS; it drains 30 s after its last Activity.

mTLS and network boundariesLocal viewAWS view

One free cert-manager CA per cluster signs everything (kind and EKS each run their own copy of this chain, so a kind cert is not trusted on EKS), and every Worker type and human gets its own common name. The frontend trusts exactly one CA file, so a cert from anywhere else is refused.

Frontend ingress

temporal-frontend-ingress in namespace temporal

  • Pods in temporal itself: 7233, 7243 (HTTP API), 6933 (membership)
  • Pods in temporal-workers labelled temporal.io/client: "true": 7233 only
  • On EKS, temporal-frontend-from-nlb: the NLB ENIs' /32s on 7233
  • Everything else, including unlabelled pods: refused

Finance egress

agent-services-worker-egress in namespace temporal-workers

  • Temporal frontend: TCP 7233
  • DNS in kube-system: 53
  • HTTPS 443 for Bedrock and STS (VPC endpoints on EKS)
  • payments-mock: TCP 8080. All else dropped

The laptop path

make pf port-forwards 7233 and the UI. A port-forward enters the pod's network namespace from the node, so NetworkPolicy does not apply to it; the TLS server name is still checked exactly as an AgentCore Worker on EKS checks it.

The AgentCore path

AgentCore ENIs can reach only the internal NLB on 7233 (sg-agentcore-worker → sg-nlb-temporal-frontend) and the VPC endpoints. TLS passes through the NLB, so the frontend itself checks the agentcore-worker cert, read from Secrets Manager at session start. The laptop reaches EKS only through the eks-pf port-forward and an API endpoint limited to its /32.
